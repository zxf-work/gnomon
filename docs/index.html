A storage engine for bi-temporal graphs

Gnomon

Ask your graph what is true now, and what you believed then.

Records get corrected. Gnomon keeps two times on every node and edge, appends each correction instead of rewriting, and answers a past belief as an ordinary question, at about the cost of the present.

Get the code See an example

The idea

One store, two times, nothing overwritten

  • Two times on every factValid time is when a fact held in the world. Belief time, also called transaction time, is when the store believed it.
  • A correction is appendedIt closes the old version with a small note and writes the new one. Not a byte of the old version changes.
  • Two questions, one storeEvery query names a point or window in valid time and, if you like, a belief time. Without one, it answers as of now.

On 5 March a bank records a transfer as active from 1 to 31 March. On 20 March it finds the transfer ended on the 15th.

On 25 March, as believed on 10 March?Active.
On 25 March, as believed on 27 March?Not active: it ended on the 15th.

Where it is useful

Built for graphs that people audit, cite and investigate

Gnomon's design targets questions like these, where the old answer still matters after the record is fixed.

Audits of transaction graphs

A payment is booked to the wrong account and fixed later. An auditor must reproduce what the bank knew on the day it cleared an alert.

Walk the transaction graph as it was believed that day, before any later fix.

Knowledge graphs with revision histories

A study run on Wikidata must be repeatable on the graph as it stood at a past revision, although editors have since corrected many of its facts.

Rerun the analysis on the graph as believed at that revision.

Investigations, entity resolution and lineage

Records get merged or corrected later: two customer records turn out to be one person, a business link ended months earlier than recorded.

How did this ring of accounts change over a month, and was that change visible at the time? What changed between two beliefs?

Performance highlights

Fast on the questions it was built for

Temporal and as-of reads of graph neighbourhoods, measured against DuckDB under a careful four-timestamp schema and other systems. At 100M edge versions, Gnomon still has the lowest median on 12 to 14 of 14 temporal queries, depending on the graph. The repository holds the comparison kit that reruns every measurement.

326×

Most of the speed comes from storage

The same queries, run as Python operators on DuckDB's storage, take a median 326 times Gnomon's time (temporal queries on one of our test graphs, 10M edge versions). Storage, more than query code, is the larger effect in 8 of 9 query families.

18.5×

Belief checked on blocks, not rows

Switch block-level belief checks off and temporal queries get a median 18.5 times slower (one of our test graphs, 10M edge versions).

0.84–1.03×

A past belief costs about the present

Past over current belief on snapshots and reachability, on our two test graphs at 10M edge versions with 10% corrections. A past belief can see fewer rows, so below 1 is not a saving.

91.2%

Hubs stay fast

Against the other systems we ran, Gnomon wins 91.2% of the instances seeded at high-degree hubs (10M edge versions), the case that per-chunk adjacency with seed growth is built for.

Quick example

Record, correct, ask twice

Gnomon is a Python package over a Rust core. Open a store directory, write versions and corrections, and pass a belief time to any operator.

One fact, one correction, two answers
import gnomon
from gnomon import OPEN_END, EntityRef
from gnomon.temporal.algebra import call_operator, ensure_all_registered

ensure_all_registered()
store = gnomon.open("quickstart-store")   # a directory; created if absent

# record: alice lives in Lyon from time 0 on (int64 microseconds)
t1 = store.assert_node("alice", "Person", {"city": "Lyon"}, vt_s=0)

# correct: we learn that alice moved to Paris at time 300
store.correct(EntityRef("node", uid="alice"), {"city": "Paris"}, vt_s=300)

def cities(as_of_tt=OPEN_END):
    env = call_operator(store.adapter, "entity_history",
                        {"uid": "alice", "as_of_tt": as_of_tt})
    return [r["props"]["city"] for r in env["rows"]]

print(cities())     # ['Lyon', 'Paris']   what is true now
print(cities(t1))   # ['Lyon']            what was believed at t1
store.close()

How it works

Four ideas under the hood

  • Corrections are notesEvery version is an immutable row; a correction appends a close note saying when a row stopped being believed.
  • Belief checked on blocksRows written together share a belief start, so a whole block of rows is checked at once and returned as row ranges.
  • Adjacency in every chunkSealed, time-ordered chunks each carry their own adjacency index, and walks grow outward from their seed nodes.
  • Operators on row rangesSnapshots, paths, diffs and counts run inside the engine and build readable rows only for the page they return.

Honest scope

What it is for, and what it is not

  • Gnomon targets temporal and as-of reads of graph neighbourhoods.
  • On workloads derived from LDBC benchmarks, and on generic joins, a columnar engine such as DuckDB is faster, by several times on generic queries at SF10.
  • Bulk loading and memory are its costs. On the SNB-derived workload it uses 3.3 times DuckDB's memory at SF10, and its bulk load is about 22 times slower.
  • A cost check refuses a call whose estimated time is over its budget. The estimate uses the seeds, hops, time window and the chunks left after pruning; at 100M edge versions it still refuses 2-hop snapshots at a past belief on a skewed graph, which take about a second when run.
  • One writer, one node, and a fixed set of operators rather than a query language.

The repository's limitations page lists the current limits in detail.
